# 原流句柄与动态流创建

恢复函数为 `004B8CE0`（118字节）和 `004B8E50`（152字节）。目标为固定解包PE，SHA256 `de41b856eb11657a27e64ea14ecdab4e1aef6518e02e7cc39d2713b260964e7a`。原始来源及Evidence ID见 `provenance-stream-creation.json`；完整Listing和270字节夹具见 `tests/stream_creation-original*`。

`4B8CE0` 从 `006BF4F0` 读取16位游标，每次以有符号16位索引调用真实分页表 `434150`。遇到type非零的表项继续递增本地游标，遇到type零才更新全局游标并将完整0x34字节清零。查表失败返回AX零且不提交全局游标。返回值只声明AX，不将未定义的EAX高位伪造为原接口。

索引零仍会正常查表、清空并把游标推进为1，然后返回AX零；创建调用方把它解释为失败。源码保留该行为，没有新增“跳过零号句柄”的规则。跨32767进入负索引时沿原分页表失败路径返回，不能改成无符号句柄映射。

`4B8E50` 原ABI为EAX=初始容量、EDI=输出short指针、栈参数=对齐标记。源接口仅将寄存器参数正规化为cdecl。它首先把reserve返回值提交到输出，然后检查零。初始容量为零时替换成2048；以tag0调用显式原分配器边界。分配失败时仍保留游标更新、已清零表项和非零输出句柄；不释放或回滚。

成功后重新查表，按原存储顺序设置data+8、容量+14/+30、blocks+2C零、type=2、对齐+4和field+10零。其余字段来自前一步0x34字节清零。第二次查表失败后原码会解引用零，源码没有引入新的错误返回。该调用中分配器重入导致表被替换/失效的故障域仍未覆盖，不宣称任意失效指针可用。

公共 `StreamState32` 是已观察的0x34前缀，`StreamRegistry32` 保留真实全局table slot，每次重新读取；它复用已恢复分页表，没有引入另一个句柄容器。

## 验证

实际MSVC Win32/x86 Release、`/O2 /W4 /WX /fp:strict`。2576组原码/源码差分比较完整分配区、每次allocate/reallocate/free参数与结果、游标、输出short和返回值。覆盖脏空表项全量清零、忙表项扫描、零号、32767边界、负short、初始容量0/1/31/2048/4097、任意对齐位、查表分配/扩容失败、payload分配失败及新/已分配表项。

原码270字节作为测试oracle，内部reserve CALL原字节不变；仅4个外调重定位至原分页表和显式allocator/memset边界，4处绝对操作数连接真实table/cursor slot。分页表的774字节原函数由共享测试装载器核验。装载器同时验证内存流片段，但这些片段不是创建函数的调用依赖。原PE入口和imports未加载执行，生产库不链接原机器码。当前验证不是完整FILE打开、流销毁、所有权或分配器压力处理的恢复。
