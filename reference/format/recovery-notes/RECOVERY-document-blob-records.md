# 文档记录块读取（00416140 及 00415CC0、00415A60）

`document_blob_records.cpp` 恢复 `00416140`（`0x416140..0x41622B`）、`00415CC0`（`0x415CC0..0x415D37`）、
`00415A60`（`0x415A60..0x415B52`）三段原字节。目标身份、三段字节及 84 字节静态表由
`tests/document_blob_records_extract_fixture.py` 按 SHA-256 核对解包主程序后写入
`tests/fixtures/document-blob-records/`。完整 LLVM Listing 在 `original.asm`，调用点与表引用在
`original.json` 和 `patches.inc`。伪代码（REA/Ghidra 线索）存在寄存器参数丢失，ABI 以 Listing 为准。

## 调用关系与 ABI

- `00416140`：EBX=文件流句柄，栈参数 `param_1=容器`。调用点 `00416DC8`（`00416D70` 段的文档成员分派），
  以 `push edi` 传容器、`add esp,4` 清理。读第一条记录（kind 应为 `0x3EC`），`param_1` 非零时把载荷交给
  `00415CC0`，再读第二条（kind 应为 `0x3ED`）。
- `00415CC0`：EAX=容器，栈参数 `(载荷指针, 载荷字节数)`。它先调用 `00415A60(3, 容器)`，然后用
  `0043CB30(字节数, tag=0)` 分配副本、`memcpy` 复制，并把 `{副本指针, 字节数}` 写入 `+0x24` 向量。
  Ghidra 写的 `FUN_0043cb30(0)` 是寄存器参数丢失造成的，Listing 中分配大小为 EBX=字节数。
- `00415A60`：EAX=表索引，栈参数 `容器`。按 `006ADDF0[索引]` 的 `{元素字节数, 增长步长, 初始容量}` 维护
  `容器+12*索引` 的 `{data, count, capacity}` 向量。元素字节数为 0 时使用 `容器+0x18` 的单块持有者。

`00415C20`、`00415E80` 也调用 `00415A60`，但它们不在本模块范围内，其索引来源未恢复。

## 容器布局

- 槽位 `k` 位于 `+12k`：`+0 data`、`+4 count`、`+8 capacity`。
- `+0x18`（槽 2 的 data）是元素字节数为 0 时的单块持有者。块由 `0043CB30(0x5C, tag=0x0A)` 分配，
  前 12 字节写入：`[0]=0`、`[4]=5`、`[8]=容器指针`。Ghidra 的 “10 字节” 是寄存器参数丢失造成的，
  Listing 中 EBX=`0x5C`（`lea 0x5c(%edx)`，EDX 为 0）。
- `+0x24/+0x28/+0x2C` 是槽 3：data 为 `{副本指针, 字节数}` 数组（每项 8 字节），count 由 `00415CC0`
  在成功后递增，capacity 为项数上限。
- 只建模上述前缀（7 个槽，0x54 字节）。文档对象的其余部分未在本模块中使用。

## 静态表 006ADDF0

- 7 项，每项 12 字节：`{元素字节数, 增长步长(有符号), 初始容量}`：
  `{0,0,0}, {4,3,1}, {0,0,0}, {8,1,1}, {4,1,1}, {0,0,0}, {1,-1,1}`。
- 表 SHA-256 为 `01bc32e3…ce16`（与 `table.bin` 一致，见 `provenance-document-blob-records.json`）。
- 第 8 项起点 `006ADE44` 是指针三元组（首值 `0x655DE0`），不是向量项，因此表项数为 7。
- 调用点只使用索引 3（`00415CC0`）。表外索引（≥7）没有原码证据，生产实现以 `std::abort` 显式拒绝，
  不作为原版行为记录。

## 分配与状态

- `00415A60` 首次分配：`bytes = count+1 与初始容量的较大值 × 元素字节数`，tag=0；失败返回 `0x64`，data 保持为空。
- 扩容：`deficit = count+1 - capacity`，若 `deficit <= 0` 不动作返回 0；否则 `新容量 = capacity + max(deficit, 步长)`，
  调用 CRT `realloc(data, 新容量×元素字节数)`；失败返回 `0x64`，原 data 和容量保持不变。
- `00415CC0`：先调用 `00415A60`。状态 `<=0` 时 count 递增并继续；`0<状态<0x14` 时返回该状态并递增；
  `>=0x14` 时返回状态且不递增。复制分配失败时撤销递增并返回 `0x64`。
- `00416140` 状态规则（Listing 为准）：
  - 第一次读返回 `>0` 时状态为该值，`>=0x14` 立即返回。
  - kind 不是 `0x3EC` 且状态 `<0x27` 时返回 `0x27`。
  - 容器非空时调用 `00415CC0`，其值与当前状态取较大者，`>=0x14` 返回。
  - 第二次读（kind 应为 `0x3ED`）以较大者合并状态，`>=0x14` 返回；kind 不是 `0x3ED` 且状态 `<0x27` 时返回 `0x27`。

## 恢复实现与适配

- `00416140`：`FUN_004BA220`（头读，ESI=句柄）、`FUN_004BA370`（载荷，ESI=物理长度）按 Listing 的读写顺序调用，
  字段为 kind、原始长度、物理长度和载荷指针。原码的局部变量未初始化，生产代码把 kind、原始长度、物理长度和
  载荷指针显式置零；原码的载荷指针在第二次读前清零。
- `00415CC0`：分配为 `FUN_0043CB30(字节数, 0, 分配环境)`，已恢复。
- `00415A60`：分配为 `FUN_0043CB30`；扩容使用分配环境的 `realloc_005EED42`（CRT realloc `0x5EED42` 的适配）。
- `memcpy`：原码调用 `0x5FB600`，它是带重叠检查的 CRT 复制例程。生产代码用 `std::memcpy`，
  并跳过零字节复制。副本块是新分配的，不会与源重叠，因此行为一致。
- 没有测试替身进入生产代码。生产实现不调用原 EXE，不包含原机器码。

## 测试

`tests/document_blob_records_differential.cpp` 在 `tests/fixtures` 中的原字节上执行原码，并把其 `call`
重定向到以下位置：恢复的 `FUN_004BA220/004BA370/0043CB30`（经 naked 桥接），CRT realloc/memcpy 的
观测桥接，以及原码内部的相邻函数。原码与恢复实现比较：

- 返回值；
- 容器的完整可观测状态（槽计数、容量、持有者内容、副本内容，以及 0x54 之后的哨兵字节）；
- 分配器调用序列（分配、realloc、释放，含大小和成功与否）。

覆盖范围：

- `00415A60`：全部 7 个索引；元素字节数为 0 的槽在持有者有/无时的分支与首次分配失败；
  元素非零的槽在空、有数据、扩容、扩容 realloc 失败时的路径。
- `00415CC0`：空与有数据的向量；字节数为 0、1、8、4097；首次分配、复制分配和 realloc 失败；
  多次追加（含 70000 字节）的数组内容一致。
- `00416140`：真实文件流与真实 `FUN_004B90C0` 打开。覆盖两条记录正确或错误的 kind、零长、奇数补齐、
  截断载荷、70000 字节大记录与截断大记录（返回 25）、无记录（EOF）、容器为空/新/已有项、
  流的粘滞状态 `-1,0,0x13,0x14,0x19,0x26,0x27,0x64`（以测试直接设置流的 `error_24` 模拟已有错误），
  以及分配和 realloc 失败。

## 限制

- 00416140 的第一次读在“头读失败”时，原码的 kind、原始长度读取的是栈残留值；测试以零填充栈模拟原码的初始残留，
  生产代码显式置零。若原版残留恰为 `0x3EC`，结果可能不同，此情形不在覆盖内。
- 状态码 `0x13/0x14/0x26` 只能通过设置流的粘滞错误模拟，真实文件路径本身无法稳定产生。
- `00415C20`、`00415E80`、`00416DC8` 及文档读分派其余部分未恢复；本模块只提供被调用的三段。
- 表外索引和容器布局之外的字段没有证据，不作保证。
