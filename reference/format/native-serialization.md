调查日期：2026-10-18。证据来自 REA 导出的 `analysis/rea-native/*.json`；本审阅没有调用 REA、切换目标或执行几何画板。原生结论与全部1,431个`.gsp`的独立字节实验相互核对，后者见 `gsp-format.md`、`gsp-summary.json`、`gsp-structure.json`。

**已把文件的 `GSP4 → 长度/类型/内容 → 偶数字节补齐 → kind900/901` 记录框架对应到真实原生函数。** 页面数量与1-based页内对象编号也得到原生静态证据。对象具体子类、2002引用的编号来源及几何求值仍未闭环，不能把这批伪代码当作完整源代码。

## Magic、28字节头与900/901

E3汇编在 `0x0041663E` 将常数 `0x34505347` 放入栈上的4字节区域；随后 `0x00416766` 令EAX=4，`0x0041676B`传入该区域地址，`0x0041676F` 调用E7写出4字节。在x86小端表示下，该常数就是 `47 53 50 34`，即全部样本的ASCII `GSP4`。

在 `0x00416787`，E3把 `0x384`（十进制900）压栈，`0x0041678D`令EAX=`0x1C`（28），`0x00416792`调用E4。这与全部样本的第一记录 `length=28, kind=900` 相同。E3伪代码没有完整保留magic暂存和寄存器参数，故此处以同一Evidence的汇编为准。

读取侧E2在 `0x00416294` 比较magic；命中后在 `0x00416388` 向E6传入最大/期望长度28，在 `0x004163BC` 检查读出的kind为900。非900分支可产生返回码`0x26`，但未据此给返回码命名。读侧同时出现`0x6B505347`（小端`GSPk`）、`0x63505347`（小端`GSPc`）以及旧版本字节交换分支；本库样本全部是`GSP4`，所以这些分支只能称作“存在的兼容读取路径”，不能称作已经通过样本验证的旧文件支持。[E2/E3]

E1的写入路径同样建立magic变量、将首个头字段设为5，调用 `FUN_004b9df0(0,900,&local_1888)`。其结束路径有 `FUN_004b9df0(0,0x385,0)`，`0x385=901`，与全部样本的零长度文件终止记录吻合。[E1]

## 两个u32、原始长度与物理补齐

E5、E4和E6为样本规则提供了双向证据：

- E5在`0x004B9DAB`令EAX=4、`0x004B9DB4`调用E7写出第一个4字节值，然后`0x004B9DC3`再次令EAX=4、`0x004B9DCA`写第二个4字节值。结合调用者的入参和E6对应读取，这两个值是原始payload长度和kind。
- E5在流状态`+4 != 0`时，于`0x004B9D96—0x004B9DA0`计算`(raw_length+1)&0xFFFFFFFE`，将结果写入输出位置；另一路保留原长度。**这是交给调用者的物理消费长度，写入记录头的长度本身仍为原始长度。** 两者不可混同。
- E4在`0x004B9E50`调用E5后，于`0x004B9E6F`按原始长度写出payload。它此前在`0x004B9E2C`准备了零字节，随后在`0x004B9E80—0x004B9E9D`按“物理长度减原始长度”的余量逐字节补零。
- E6在`0x004BA125`和`0x004BA139`分别调用E8读4字节。其`0x004BA144—0x004BA150`检查同一流状态`+4`并计算偶数长度，然后依调用者缓冲区长度读取或跳过剩余内容。[E4/E5/E6]

因此样本遍历公式获得原生支持：

```text
记录头 = u32le 原始payload长度 + u32le kind
磁盘payload占用 = (原始payload长度+1)&~1  # 本批文件采用的对齐模式
下一记录 = 当前偏移 + 8 + 磁盘payload占用
```

这与1,431文件/1,907,414记录全部抵达EOF、457个单字节补零的实验一致；也解释了为何“长度字段已含补齐”的假设不成立。原生代码有可关闭对齐的流状态分支，故不能把“所有潜在流都强制偶数字节对齐”作为全软件规范；目前严格保证的是本批`.gsp`文件与观察到的条件路径。

E6还区分原记录短于、等于或长于调用者给定容量的情形，并出现返回码3/4。这表示记录读取器不只是无条件`memcpy`。没有完成错误码表恢复，因此仅记录分支，不给3/4赋予完整业务名称。

## 文档头与页面数量

在E1构造的28字节kind900 payload中，`local_1888=5`；紧随其后的16位值来自文档状态`+0x10`，随后代码按该值循环，逐项从文档数组中取页面候选并调用E9。这样，样本中绝对偏移`0x0E`的u16（payload+2）与页面区间数一致，获得了独立的原生静态支持。

E3根据模式值0/1/2生成头字段1/4/5；E2对读出的头首u16做`<4`、`>5`等条件检查，同时对另一个16位兼容字段做`>5`检查。这支持将`file[0x0C:0x0E]`称为格式/布局版本字段，而非仅凭magic尾字符推测版本。仍不能把这些值直接当作界面产品版本号。[E1/E2/E3]

E1还在写页前建立兼容容器信息，再在各页后写kind`0x387=903`。写入流水线出现`0x3EE=1006`与`0x3EF=1007`的成对调用，和样本中900/901之外的嵌套边界一致。它另有`0x3EC=1004`与`0x3ED=1005`分支，而本批1,431样本没有该kind；这恰好说明样本覆盖不等于格式全部能力。尚未确认这些分支的业务对象名称。[E1]

## 1-based对象编号与2002引用候选

E9从页面状态`+0x110`开始遍历链表，每个对象的下一项从`+0x84`取得。第一轮清零每个对象的`+0xC4`并统计数量；第二轮设置计数器从1开始，将`1,2,...,N`写入这些对象的`+0xC4`，并构造包含对象指针的工作表，然后调用 `FUN_004a80f0`。它还把对象总数写入页面状态`+0x290`。[E9]

这是**原生保存路径明确建立1-based页内对象编号**的证据，不只是Java运行库的类比。它与独立样本观察相容：kind2002所有370,457条都符合`u32 count + u32[count]`；最小样本的第三个对象含向量`[count=2,1,2]`，前两个对象分别含两个double的位置数据。

不过，目前E9没有直接展示“从对象+0xC4取编号并写入kind2002”的那一步，因此这里仍保持引用候选边界；也不把Java genera常量0/2等同于整个原生对象类型枚举。应继续检查`0x004A80F0`及其对象写入分发，才能确认具体kind2000/2002/2201语义。

## MFC边界与反编译完整性

E1使用`CArchive`，可见模式分支、`CArchive::Read(...,8)`和最终`CArchive::Write(buffer,length)`。它的保存分支先调用GSP内部写入器构建数据，再把所得缓冲区交给MFC归档写出。这个边界说明GSP记录框架有自己的序列化层；它不应被简化成“MFC默认对象归档格式”。

所有结论都是静态观察与样本核对，没有实际观察保存、加载、UI或几何求值。REA自己的limitations特别记录了Ghidra的`hasNoReturn`属性对控制流的影响：

- E1：`0x004F644F → 0x005EDDB9 _free`被模型标为终止调用；`0x004F64A4 → 0x005BFF5A`也被标为终止。伪代码另报移除了`0x004F6474`的不可达块。它的函数body因此是多个不连续区间，而非一个已证完整流程。
- E2：`0x004165B4`、`0x004165D7`、`0x004165EA`到`_free`的调用被标为终止；错误清理分支和后续fallthrough可能不完整。不能据伪代码表面上的重复释放或早停直接定性为真实缺陷。
- E9的伪代码也在清理数组和释放工作表处标`_free`为“不返回”；正常释放后的状态恢复流不能仅按这份伪代码重建。

这些标记只记录Ghidra FunctionManager的判断，REA明确没有独立证明被调用函数不返回。寄存器调用约定也会造成伪代码漏参，例如E4看似只有一个参数，而E3的汇编明确同时传入长度、kind与payload指针；E3伪代码甚至省去了仍可在汇编看到的magic写入。因此本报告需要时优先引用同一Evidence中的Listing，不把`FUN_...`伪代码原型当作可靠ABI。

本文支持容器、28字节文档头、padding和记录层的静态解释，不单独证明完整对象写回或几何重建。对应源码和验证范围见[恢复说明](../recovered/README.md)，任务顺序只见[总计划](../recovered/PLAN.md)。
