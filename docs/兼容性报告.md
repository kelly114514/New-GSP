   - 决定性夹具（`tools/r19-font-fixture.ts`，把 0092 里原版写的“宋体”条目改写后让原版另存）：按新版现在的写法 `[u16][名字]`（8 字节，名字后没有 NUL）→ 5 段宋体全部变成 Tahoma；只补上 NUL（`[u16][名字][NUL][补齐]`）→ 全部保留。新版写入用的长度是 `(名字字节数 + 3) & ~1`，名字字节数为偶数时正好不留结束符。

   - 另一类原因是名字本身：在 1000 上把“宋体”条目换成英文别名 `SimSun`、`Microsoft YaHei`（带结束符），引用它的样式行消失（推断并入了参数相同的 Tahoma 行）；换成中文名“微软雅黑”则保留。1400（4.x 工具文件，GBK 编码的“宋体”“黑体”）另存后变成 Tahoma。已测到的规律是：UTF-8 中文名保留，英文别名和 GBK 名不保留；其它字体没有逐一测。
   - **现有风险（推断，未用原版验证）：** 任何偶数字节名字的字体经新版完整重编码后，原版都可能读成别的名字而换成 Tahoma，而保存保护只拦了名单里的几种。全库字体表里偶数字节的有 Symbol（29 份）、Trebuchet MS、Arial Narrow、System 等。新版自己读回是按记录长度截取的，所以往返审计看不出来。
   - 顺带更正：`1201` 的首个 u16 不是“首条为 1”，而是字体自己的属性（Times New Roman 在任何位置都是 1，Arial 0，黑体/楷体多为 4，Symbol 9，Wingdings 8，Tahoma 0 或 32）；原版在名字后除了结束符还有一个 u16。把首个 u16 写成 1 的“宋体”夹具在 1000 上仍保留。
2. **动画按钮的自定义速度值不是每秒像素。** `tools/r19-button-survey.ts`：631 份课件有动画按钮，其中 207 份用了慢（4）、中（24）、快（80）以外的浮点值。新版把这个值直接当每秒页面像素（`anim.ts` 的 `animationSpeedPx`），而三档预设实测是 4→35、24→105、80→175 像素/秒，不成比例。全库最常见的自定义值是 0.00187（52 份）、1.2（48 份）、0.3（28 份），另有 288、1920、307000 等；按现在的算法（`anim.ts` 每帧位移 = 该值 × 帧间隔，路径点和自由点都是）前三种每秒不到 2 像素。这些值集中在 5.1 版文件，不是旧格式遗留；多数是 1.2 的整数倍（1.2、96、288、1920）。未做原版夹具，换算规律未知（`tools/make-anim-fixture.ts` 加 `probe_anim_speed.py` 可以直接量）。
3. **移动按钮的速度没有实测依据。** 598 份课件有移动按钮（高速 443 份、中速 290 份）。`anim.ts` 的 `PX_PER_SEC`（50/120/260/600）在文档里找不到测量记录；`real_move.py`、`real_move2.py` 采的是四档的文件编码。参数动画（87 份）的速率第十八轮已知未定标。
4. **剩余截图差距集中在文字和坐标系。** `tools/r19-score-features.ts` 按当前页含有的对象分组：有说明文字的 873 份平均 0.9321（没有的 0.9637），有坐标系的 692 份 0.9342（没有的 0.9539），用中文字体的 179 份 0.9234，有函数图像的 69 份 0.9172；有轨迹、迭代象、弧、参数颜色的课件与没有的持平或更高。这只是相关性（得分是墨迹重合比例，墨多的页天然高），不能当作可回收的分数。

## 迭代数值快路径

2026-11-11。目标是只提速、不改结果：Mira分形-三鹰翅.gsp 的着色轨迹有 500 个采样，每个采样做 9,999 层单映射迭代，旧代码对每层的每个对象都走通用求值（分配 Q、Result、Map 查表）。

做法（[engine.ts](../src/core/engine.ts) 的 `evalSingleMapLastIterPoint`、新增 [iterfast.ts](../src/core/iterfast.ts)）：

- **只留末状态。** 轨迹链里读取这个迭代的只有迭代象、迭代象又只被迭代点读取时，缓存里不再保留 9,999 层状态；各迭代象的末点在末状态上都核对过，任何一个在末状态上求不出末点（原本要往前找前一层）就回到完整保留重新求值。
- **数组式查表。** 迭代体里用数组和代数戳代替每层新建 Map 和 `memo.clear()`。
- **数值编译。** 迭代体只含“计算（含用户函数调用）/ 横纵坐标度量 / 按坐标画点”、无单位、没有位置覆盖时，编译成对 `Float64Array` 的直接运算（度制和弧度制均支持）。运算顺序和舍入与 `expr.ts` 的求值一致；中途出现无定义、非有限数、坐标系退化、单位不是无单位、对象或函数定义被替换等任何不寻常情形，立刻退回通用求值器从当前层继续，所以边界行为不变。反三角函数（结果带角度单位）、极坐标绘点、导函数、函数递归都不在快路径内。

## 通用迭代与交点求值

2026-11-11 对多映射、大量迭代象的课件，密集对象编号使用数组保存每个迭代状态的对象结果，稀疏或异常编号仍用原来的 Map；同时把交点求值里不依赖调用状态的函数移出热循环。没有改变迭代层数、采样数或几何公式。

`IFS-4_circles_limit_set__4.gsp`（156 个对象，240,000 个迭代图形）用同机 Node 打包版单次测得整页求值约 4.96 秒降到 2.44 秒，优化前后逐对象指纹一致；测试负载有差异，该数字不是稳定基准。数组查表修正后、交点热循环调整前，Chrome 源码模式下移动自由点 36 的三个位置，每次只重算一次，分别约 3.07、3.34、3.09 秒；最终位置的 240,000 个图形及完整结果 SHA-256 与同位置完整重算一致。浏览器测量时有整库验证并行，不包括真实桌面输入、绘制或显示刷新；交互性能仍需继续优化。复测脚本见 `tools/perf/mira-bench.ts` 和 `tools/perf/ifs-browser.ts`。

数组查表和交点热循环调整后，以修正重复重算的调查脚本复核全库 2,421 个非空页面，其中 2,352 页模拟移动自由点；打开及移动后的聚合结果 SHA-256 为 `702a4b8b482394495a53be537ebfb4e9e7e953a20ad91164e46d3dced6aeb3a4`，与改动前一致，0 页报错。并行测试时，单次移动重算中超过 100 毫秒的有 284 页；结果受负载影响，不包含绘制和真实鼠标输入，不能直接视为用户实际帧率。

### 互读中发现并修复的问题

- 原版拒绝**带引用的计算同时有位置记录（2211）**的文件：二分实验定位后，写入器对带引用的计算不写 `2211`。
- 原版另存时会按计算结果的单位重写计算的类型号（无单位 51、距离 48、角度 49）：写入器改为依结果单位写。
- 参数的数值是令牌而不是 f64（见 `docs/gsp格式.md` §4）：用不同数值的样本（7、2.5、−4、12）对照得出。
