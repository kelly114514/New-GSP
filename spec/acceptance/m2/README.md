## 1. 复跑

```powershell
$py = "tools\oracle\.venv\Scripts\python.exe"

# 1) 从原版导出清单生成用例（不启动原版，只读 manifest + EMF + HTML）
& $py tools\emf_match.py batch --manifest oracle\full\manifest.jsonl --out oracle\m2-cases-r2

# 2) 用实现方的适配器逐例求值并比对
& $py tools\check_m2.py --index oracle\m2-cases-r2\index.json --report oracle\m2-report.json `
    --runner node impl\packages\core\scripts\geometry-dump.ts "{input}"

# 3) 只跑随仓库提交的 6 个基准用例（CI 里的 --self-test 只验比较器自身）
& $py tools\check_m2.py --index spec\acceptance\m2\baseline-index.json `
    --runner node impl\packages\core\scripts\geometry-dump.ts "{input}"
```

`emf_match.py batch` 的 `--max-emf-bytes`（默认 50 MB）会跳过超大 EMF：分形目录里有 70 MB 以上的单文件，它们的对象数动辄数万，跳过时记为覆盖缺口，不算失败。

## 3. 这个数字应该怎么读

- **能断言的部分，在放宽拟合的分析里零系统性反例；严格口径的断言还没有对实现跑过**，不能据此说「实现与原版一致」。
- 「非活动页」A 组 47,302 + C 组 34,072 是原版导出能力的硬限制（只导打开后的当前页），不是实现缺口；多页文件的完整验收需要切页导出，见 `tools/oracle/README.md` 第 7 节。
- 保守的平移拟合（只用自由点颜色投票，唯一才接受）让 A 组约 4,360 个、C 组约 2,050 个本可断言的对象落入 `ambiguous_translation` / `no_free_point_anchor` / `insufficient_translation_anchors`。`tools/m4_survey.py` 里的「分析用」拟合（用预测的点/圆/线段打分，要求唯一最高分）能救回其中一部分，但那会让预测参与对齐，所以**没有用于提交的断言**，是否放宽由规划者决定。
- M2 的验收门槛仍建议写成两句：**可断言集合全部通过**；**可断言集合的占比随 C/D 组推进上升**，每轮记录一次。隐藏对象永远不会有 EMF 期望，只能用 HTML 构造文本或原版度量对话框补足（见 Q4）。
