## Q6（M2 core）：弧、扇形、弓形的交换格式，及弧相关的未验证边界

实现方在 `geometry-dump.ts` 输出里为弧与弧内部加了字段。验收协议 [acceptance/README.md](acceptance/README.md) 的 kind 表还没有这些类型，请规格方（W2 的比较器）对齐，或告诉我要改成什么。

**交换格式（`gsp-core-geometry-v1` 的扩展）：**

| kind | geometry | 说明 |
|---|---|---|
| `arc` | `{center:[x,y], radius, startAngle, sweepAngle, start:[x,y], end:[x,y]}` | 约束 79/80/81 |
| `sector` | 同上 | 约束 82，父弧加两条半径闭合 |
| `circular-segment` | 同上 | 约束 83，父弧加弦闭合 |
| `segment`（带 `degenerateArc:true`） | `{a,b}` | 约束 81 的共线/半径超过 30,000 的线段分支；`parameterizationKnown:false` |

- `startAngle`、`sweepAngle` 是**数学角**（弧度）：`angle = atan2(−dy, dx)`，页面点 `center + radius·(cos a, −sin a)`；`sweepAngle > 0` 表示在页面上看起来逆时针，符号带方向，|sweepAngle| 在 (0, 2π) 内。
- `start`、`end` 是弧端点的页面坐标，由角度推出。**建议比较器比较 `start`/`end`/`center`/`radius` 和经过的一侧（例如弧中点），不要直接比角度**：方向约定是〔静态证据〕，原版若证明相反，只改内核里一个常量（`impl/packages/core/src/arc.ts` 的 `ARC_ORIENTATION`），端点会随之互换，而比较器不用改。
- 弧中点可由 `center + radius·(cos, −sin)(startAngle + sweepAngle/2)` 得到。

**内核返回 `unsupported` / 不存在的弧相关边界（都需要原版实验或更多静态证据）：**

| 约束 | 条件 | 当前结果 |
|---|---|---|
| 79 | A 或 B 不在圆周上 | 已实现（M5，卡片 79 的合成输入证据）：半径取 `\|OA\|`，B 只给终方向；A 与圆心重合时 `not-existing: arc-start-point-coincides-with-circle-center` |
| 79 | A=B（整圆还是零弧） | `unsupported: arc-coincident-endpoints-unverified` |
| 80 | O=A 或 O=B | `not-existing: arc-center-coincides-with-direction-point`（卡片说“无定义”） |
| 80 | `\|OA\|`≠`\|OB\|` | 已实现（M5，卡片 80 的合成输入证据）：半径取 `\|OA\|`，B 只给方向 |
| 80 | A、B 同方向 | `unsupported: arc-coincident-directions-unverified` |
| 81 | A=B | `not-existing: coincident-arc-endpoints` |
| 81 | 共线或半径/圆心坐标超过 30,000，M 在弦内（沿 A→B 的投影严格在 0 与 1 之间） | 线段 A→B，`degenerateArc:true` |
| 81 | 同上但 M 在弦外 | `unsupported: three-point-arc-degenerate-middle-outside-chord-unverified` |
| 82/83 | 父是 81 的线段退化分支 | `unsupported: arc-interior-of-degenerate-arc-unverified` |
| 15 | 多边形参数 s 不在 [0,1]（边比例） | `unsupported: native-polygon-parameter-out-of-range-unverified` |
| 15 | 多边形边序号 ≥ 顶点数 | `unsupported: native-polygon-edge-index-out-of-range` |
| 15 | 81 的线段退化分支作为路径 | `unsupported: path-direction-and-unit-unverified` |
| 11/12 | 弧父有两个合法候选（线在弧范围内的两个根） | `unsupported: intersection-arc-root-order-unverified` |
| 13/14 | 弧父有两个合法候选 | `unsupported: intersection-arc-root-order-unverified` |
| 13/14 | 圆与 81 的线段退化分支有两个合法候选 | `unsupported: intersection-degenerate-arc-root-order-unverified` |

只有一个合法候选时（另一个落在线段/射线范围或弧范围之外），11/12、13/14 返回这一点，两个 ID 结果相同；这与卡片“只有一个合法候选时两 ID 可能得到同一点”一致。

- 问题：弧父的两个合法候选时 11/12、13/14 各取哪一个（卡片只说“方向符号参与选择”，没给公式）；81 共线时 M 在弦外是否有效；79 的 A/B 偏离圆周时是投影还是不存在；多边形上 s 超出 [0,1] 的含义。
- 需要：原版对这些边界的实验结果，或 EMF/拖动证据。
- 卡住：弧相关交点在“两个合法候选”状态下的验收；其余正常几何不阻塞。

**规格方答复（Q6 的交换格式部分，2026-10-24）：**

- 交换格式已按本条采纳，写入 [acceptance/README.md](acceptance/README.md)：`kind` 取 `arc`、`sector`、`circular-segment`，字段 `center`、`radius`、`startAngle`、`sweepAngle`（弧度，数学角，`sweepAngle>0` 为页面上看起来逆时针，带符号）和可选 `start`/`end`；退化的 81 若按线段输出，`kind` 取 `segment`，可附 `degenerateArc`、`parameterizationKnown`，比较器忽略这两个标志。`tools/check_m2.py` 的比较器按「逆时针覆盖区间」比较圆心、半径、区间两端点和区间中点，因此 `sweepAngle` 的符号写法不限，取成补弧（方向写反）会失败。期望值来自原版 EMF 弧/扇形/弓形图元，已归一成 `sweepAngle>0`。
- 弧的方向约定已由原版 EMF 验证，不再是静态证据：79/80/81 都是页面上看起来逆时针从第一端点 A 到第二端点 B（81 是经过 M 的那一段，可顺可逆），见 [79.md](objects/cards/79.md)–[81.md](objects/cards/81.md)。实现里 `ARC_ORIENTATION` 常量不必改。
- 仍然〔未知〕、语料保存状态里**从未出现**、只有拖动才会出现的情形：80 的 |OA|≠|OB|（语料 506 个可求对象最大偏差 4.7e−12 px）、79 的 A/B 偏离圆周（223 个对象最大 1.2e−5 px）、81 共线/半径超过 30,000（183 个对象最大半径 9,162）、A=B 同方向、弧交点在「两个合法候选」时的选择（13 个弧父交点对象里每次都只有一个根在弧上）。实现保持当前的 `unsupported` 处理是对的；要确定这些，需要用户同意的原版实验，建议见各卡片的「建议原版实验」。
- 已验证、可以去掉 `unsupported` 的：15 在多边形上的 `s∈[0,1]`（46 个可见点）；15 在弧上按 `t·sweepAngle` 从 A 起算（55 个可见点）；11/12/13/14 弧父的回退规则（首选根不在弧上时取另一个，10 个对象）。多边形 `s` 超出 [0,1] 的含义〔未知〕，保持现状。

## Q7（M4 第一批）：零比例与非共线三点比的边界

- 问题：30/32 的比例为 0 时，点、线、圆与区域是否都存在，塌缩像是否可作为路径、镜面或圆的半径来源？32 的 D、E、F 不共线时使用距离比还是沿 DE 的投影比？卡片明确这些尚未验证。

## Q8（M5 第一批）：数值求值的四处空白

- **Q8.1 单位字形**：`10042` 的 1 与 2 都显示 `°`，`U+F0B0` 只在对象字体是 `Symbol` 时出现（语料 42 例 `°`、6 例 `U+F0B0`，无例外）。规格方答复：字形查对象样式链 `2008 → 1203[fontIndex] → 1201`，字体名以 `Symbol` 开头即用 `U+F0B0`，否则 `°`；`10042=0` 一律 `弧度`。已写入 [acceptance/m5-measures.md](acceptance/m5-measures.md)。
- **Q8.2 `10041=0/2` 的字形字符串**：语料里所有带度量对象的页面都是 `10041=1`（厘米），像素与英寸两种没有原版样本。规格方按任务书给定的码位含义取 `像素`/`英寸`，标为低置信；要提级需一次页面单位切换的原版实验。
- **Q8.3 负数半值舍入**：0.635→`0.63`、5.715→`5.72` 证明按 double 精确值的四舍五入（half away from zero）。负数的半值样本 0 例（语料只有 −123.11 这类负读数，不在半值上）。实现取 half-away-from-zero，并在 `questions.md` 保留此条待实验。
- **Q8.4 约束 15 的参数与原版 EMF 不一致**：`分形艺术/Arboresent.gsp` 对象 15（线段 14 上的点）存档 `2003` 的 f64 为 0.68476，按此算出的三点角（对象 16，父 `[15,7,10]`，顶点 7）为 17.50°；原版 EMF 文字是 21.83°，反解要求参数约 0.59942。全语料**没有一个**约束 15 的点被原版几何断言覆盖，所以这条无法用几何断言判定谁对。影响该文件 2 条 measure 断言（16、20）。另外 `2003+2` 处现在被当作"父 genera"校验，本例中它同时等于父对象序号（都是 14），两种解释无法区分；建议后续用父序号与 genera 不等的样本定夺。

**需要**：原版对 15 号点的拖动/重存实验（一次即可分辨 0.6848 与 0.5994），以及一次页面单位切到 px 的导出。

**卡住**：只有 `Arboresent.gsp` 的 2 条 measure 断言与像素/英寸字形；本批其余 2,332 条不受影响。

## Q9（W1 提问）

- **Q9.1 约束 48 的显示量纲该听谁**：48 卡片写“实现应按自己的求值量纲核对 genera，不一致时不要用 genera 覆盖算出的值”，而本批任务书与实现契约的口径是“量纲由对象头 genera 定，值只由表达式决定”。全语料里两者不一致的对象有 184 个（例如 `P0*P1`、`P0^2`，表达式推出 `area`，genera 是 51）。当前实现取 genera 的量纲做 `displayUnitText` / `internal.dimension`，把表达式量纲放在 `internal.expressionDimension`，并置 `internal.dimensionMismatch`。需要确认原版这类对象显示的是空单位还是 `厘米²`；若原版按表达式量纲显示，改动只在 `measure.ts` 的 `evaluateCalc` 一处。
- **Q9.2 2307 的 36 字节变体**：语料有 2 条 `2307` 载荷长 36、`+28` 为 6。§8.11 明确 36/40 字节变体未解、不得按 32 字节静默截断，实现报 `unsupported: 2307-layout:36`。若这两条有原版读数断言，需要给出 36 字节布局或明确把它们排除。
- **Q9.3 缺失 `+28`**：契约只确认 0..5；任务书要求字段缺失时按 2 处理。语料所有 32 字节 2307 与全部 2311 都有合法值，该回退未在真实对象上触发；需要一份没有该字段的样本才能确认原版缺省精度。
- **Q9.4 面积单位文字**：验收表把面积整行标为“本批不验收”，没有给出 `displayUnitText`。实现暂用 `厘米²`/`英寸²`/`像素²`（长度单位 + U+00B2），`internal.magnitude` 用 px²。上标布局与字形需要原版样本才能升级。
- **Q9.5 39/46 的父类型边界**：39 卡片只列“多边形/扇形/弓形内部”。实现接受 `polygon`、`sector`、`circular-segment`，扇形/弓形要求 `startAngle/sweepAngle/start/end` 齐全，其它类型返回 `unsupported: 39-parent-type:<kind>`。46 卡片写“圆或弧 C / 圆内部/弧内部取其边界半径”，实现接受 `circle/disk/arc/sector/circular-segment` 的 `radius`。若原版对“弧内部”另有定义，需要一次构造实验。
- **Q9.6 36 的父是 81 退化弧**：81 共线时几何层输出 `segment`（带 `degenerateArc`）。实现把这种父从 36 里排除（`unsupported: 36-parent-must-be-segment`），因为卡片 36 的父模板是线段 S。需要原版确认“退化弧作线段长度”是否允许。
- **Q9.7 未知运算符 `0x1005`**：`20 虚线工具.gsp` 页 3（0 起页 2）对象 250、306 的 2311 含 `0x1005`（形如 `0x1005 P0 / P0`）。按“不得凭猜测吞掉 token”报 `expression-unsupported:0x1005`；若它其实是“负号/正号”之外的一元运算，需要规格补 token 表。
- **Q9.8 负零的显示**：实现按 C 运行库 `printf("%.nf")` 的行为，`-0.004` 在 2 位精度下输出 `-0.00`（`displayValue` 为 `-0`，与 `0` 相等）。全语料有 53 个对象落在这一档（角度 24、无量纲 25、长度 4）。原版是否把负零改写成 `0.00` 没有任何样本证据；若要改，只需在 `measure.ts` 的 `roundedText` 里把舍入后为 0 的文本去掉负号，改一处即可。
- **Q9.9 `9008` 的位置**：交接信息说 `9008` 是文档级记录，但格式规格 §7.6/§9 与实测一致地把 `9008` 放在**页容器**里：全语料 1,431 文件 / 2,455 页，`9008` 出现在页容器 2,455 次、文档节点 0 次，也没有任何页缺它。实现以页容器为准，另加了可选的 `dpi` 参数与文档级回退（`evaluatePageGeometry(page, dpi?)`、`PageGeometryEvaluator(page, dpi?)`、`toGeometryJson` 从文档节点扫 `9008`），页面自己的值永远优先；该回退在当前语料下一次也不会触发。
- **Q9.10 非 96 DPI 的度量**：验收 §求值模型 6 要求“`9008` 非 96 且需要 DPI 的换算”按值算不出来处理，实现据此报 `unsupported: page-dpi-non-96:<dpi>`（缺 `9008` 报 `page-dpi-missing`，纯像素页面不需要 DPI）。语料里只有 `Support Files/Example Tools.gsp` 的 10 个页是 72 DPI（`10041=1` 厘米页），上面共 13 个数值对象，其中 2 个长度度量本来也因父对象未实现而失败，所以当前 0 条可用读数受影响；若原版在 72 DPI 页确实按 `72/2.54` 换算，应改回直接使用保存的 DPI。

**规格方答复（2026-10-24，W1 完成验收后）：**

- **Q9.1 采纳实现的选择**：显示量纲听对象头 genera，表达式量纲只作诊断。理由：genera 是原版自己写进对象头的显示量纲记录，若改用表达式量纲，这个字段就没有意义；全语料 184 个「表达式量纲 ≠ genera」的 48 对象里**没有一个有原版读数断言**（已核实），现有证据无法判定，因此按 genera 显示并登记为未验证项。要升级需原版对 `P0*P1`（genera=51）这类对象导出一张图，看显示的是空单位还是 `厘米²`。
- **Q9.2**：36 字节 `2307` 只出现在 `Tool Folder/29 滑块工具.gsp`（4 个对象，约束 47），该文件**没有断言**。保持 `unsupported: 2307-layout:36`，不猜布局。
