# 实现方提出的规格空白

格式：问题 / 需要什么 / 卡住了哪个功能。规格方回答后移到对应规格里。

## Q1（M1 core）：布局 4 文件怎样自动选择 GBK 还是 Big5？

- 问题：规格 §6.1 说布局 4 的文本是 Windows ANSI、代码页不记录，语料里 20 个文件是 GBK、1 个（`example-39.gsp`，页名）是 Big5。读取器没有可靠依据自动区分（GBK 能“成功”解出大多数 Big5 字节，只是变成乱码）。
- 现状：core 默认按 GBK 解码，`readDocumentModel(doc, { ansiEncoding: 'big5' })` 可改选；原始字节始终保留，不影响无损读写。
- 需要：原版在“布局 <5”时怎样决定代码页（§12 第 7 条已列），或一个可靠的启发式（例如按 9004 构建串、字体名、字符集字段）。
- 卡住：只影响布局 4 文件的页名/标签显示，M1 不阻塞；M3 打开旧文件时需要。

## Q2（M1 core）：900 头 [11]（文本编码 ID）与布局版本谁说了算？

- 问题：§6.1 说编码由 [11] 指定（9=UTF-8，3=ANSI），语料中 [11] 与布局严格对应（布局 5↔9，布局 4↔3）。任务要求“布局 5 → UTF-8，布局 4 → GBK/Big5”，实现按布局版本选择，没有读 [11]。
- 需要：如果将来出现布局 5 但 [11] 不是 9（或布局 4 但 [11]=其它）的文件，应以哪个为准；其它 ID 对应的代码页表。
- 卡住：目前没有样本，不阻塞。

## Q3（M1 core）：读取器对非 page/tool/group 类型的 902 信封要不要同样严格校验提示串？

- 问题：§5.5 的崩溃条件针对读取方“找下一个串”的逻辑，该逻辑对所有信封类型相同（§5.4 里未知类型也要显示串 0）。实现对**所有** 902 载荷按 §5.2 严格校验并拒绝不合规者（含类型 0、3、4、≥6）。
- 需要：确认这个选择；或说明类型 3（1004/1005 块）等信封的载荷是否可能没有三个提示串。
- 卡住：语料没有这类信封，不阻塞。
