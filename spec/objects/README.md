# 对象目录

对象目录把 .gsp 文件里的对象类型（外部约束 ID）和三类资料连在一起：原程序数据表中的约束行、资源字符串中的描述模板，以及语料里的实际用例。

| 文件 | 内容 |
|---|---|
| `catalog.json` | 机器可读的完整目录，schema `gsp-object-catalog-v1` |
| `catalog.md` | 由同一份数据渲染的表格，每个约束一行。由生成脚本写出，请勿手工编辑 |

约束表有 123 行，语料（`original/sketchpad5/` 中 1,431 个 .gsp 文件，400,744 个对象）中用到其中 113 个。未用到的 10 个也保留在目录里。

证据等级按 `spec/README.md` 标注：**已验证**（原版实验或全语料检验）、**静态证据**（来自原程序数据或资源，未经原版实验）、**推测**。

## 重新生成

在仓库根目录运行（只用标准库，Python 3.13）：

```
python -I tools/build_object_catalog.py
```

输入都在本机，不入库：`original/sketchpad5/`、`reference/format/recovery-object-dispatch.json`、`reference/features/resource-text.json`。脚本依赖 `tools/inspect_gsp.py` 的 `parse_records`。同一输入重复运行，输出字节相同（已验证）。

脚本遇到以下情况会报错退出，不写任何文件（已验证：当前语料没有触发）：

- 某个 .gsp 记录解析中断；
- kind 2000 嵌套，或未被 2007 关闭，或 2007 没有对应的 2000；
- 约束行里的选择字段与原始字节不一致。

语料中出现、但约束表里没有的外部 ID 不算错误，写入 `unknown_ext_ids_in_corpus`。当前为空（已验证）。

## catalog.json 字段

### 顶层

| 字段 | 含义 | 证据 |
|---|---|---|
| `schema` | 格式版本，固定为 `gsp-object-catalog-v1` | — |
| `generated_by` | 生成脚本的路径 | — |
| `inputs` | 两个 JSON 输入的 SHA-256，键为仓库相对路径。输入变了，目录要重新生成 | 已验证 |
| `corpus.root` | 语料目录，相对仓库根 | — |
| `corpus.files` | 扫描到的 .gsp 文件数（扩展名大小写不敏感） | 已验证 |
| `corpus.objects` | kind 2000 记录总数，与 kind 2007 数相同 | 已验证 |
| `constraints` | 每个约束一项，按 `ext_id` 升序 | — |
| `unknown_ext_ids_in_corpus` | 语料中出现、约束表里没有的外部 ID，升序 | 已验证（当前为空） |
| `genera_taxonomy` | genera 表的 90 行原始数据，每行 `index` 与 6 个 u32 | 静态证据（原始值） |

### constraints 中每一项

| 字段 | 含义 | 证据 |
|---|---|---|
| `ext_id` | 外部约束 ID。.gsp 中 kind 2000 载荷开头的小端 u16 就是它。语料里出现的 ID 全部在约束表中 | 已验证 |
| `table_row` | 该行在约束表中的序号（表内行号，不是文件里的值） | 静态证据 |
| `main_kind` | 约束行的第 2 个 u32（原程序内部编号） | 静态证据；含义推测 |
| `genera` | 约束行的第 3 个 u32（原程序内部编号） | 静态证据；含义推测 |
| `parent_template_index` | 父模板指针表的下标，取自约束行字节偏移 0x12 处的 u16 | 已验证（脚本检查过 123 行的字段与原始字节一致）；作为下标的用法静态证据 |
| `parent_template_words` | 指针表该项的原始 u32 词，截到第一个 0（含）；没有 0 则保留全部。下标越界时为 null | 静态证据（原始值）；含义未解码 |
| `description_template_index` | 约束行字节偏移 0x18 处的 u16（即 u16 下标 12） | 静态证据 |
| `description_template_id` | 资源字符串 ID，等于 4416 加上上一字段 | 静态证据（映射） |
| `description_template` | 资源字符串原文。`^A`、`^B` 等标记按原样保留，不解释。该 ID 不存在时为 null | 静态证据；标记含义推测 |
| `object_count` | 外部 ID 等于本项的 kind 2000 记录数 | 已验证 |
| `file_count` | 含至少一个这类对象的文件数 | 已验证 |
| `child_records` | 2000 与 2007 之间的子记录，按 kind 数值升序。每个 kind 下有 `count`（总数）和 `sizes`（载荷长度 → 次数，长度也按数值升序） | 计数已验证；kind 的含义多数未知，见 `reference/format/gsp-format.md` |
| `example_files` | 含本类对象的文件中，体积最小的最多 3 个。路径相对 `original/sketchpad5/`，用 `/` 分隔 | 已验证（仅供查阅） |

描述模板与对象含义一致（静态证据）：外部 ID 1 为“是……的中点”，2 为“线段”，3 为“圆”（以圆心定义），15 为“上一点”。

## catalog.md

每个约束一行，列依次为 ext_id、main_kind、genera、父模板词、对象数、文件数、描述模板。父模板词为 null 时写“越界（索引 N）”，描述模板为 null 时写“（无）”。内容与 `catalog.json` 一致。

## 已知限制

1. **描述模板缺失（静态证据）**。`resource-text.json` 中没有 ID 4567–4592 这一段，而 15 个约束的描述 ID（4568–4577）落在其中。这 15 个约束是：0、43、44、47、48、62、72、75、76、84、85、89、99、100、108。其中 48（49,419 个对象）、0（30,287 个）、62（14,312 个）的对象数最多。`PLAN.md` 附录 A 也提到 0、48、62 没有描述模板，与此一致。缺失的原因未知：可能是资源抽取不全，也可能原程序这里确实没有模板（推测）。

2. **脚本步骤模板未收录（静态证据）**。在 `reference/` 和资源文本中没有找到清楚的映射，按规则跳过，没有猜测。

3. **父模板词未解码（静态证据）**。`parent_template_words` 是原始数字。以下只是推测：值 90 以上（如 95、96、97、99、100）可能是重复或计数代码（推测）。例：外部 ID 1 为 `[14, 0]`，外部 ID 2 和 3 为 `[95, 4, 0]`。

4. **下标 62 越界（静态证据）**。指针表只有 62 项（下标 0–61），但外部 ID 62、76、89 的父模板索引是 62，因此 `parent_template_words` 为 null。它可能表示“没有父模板”，也可能是抽取时少了一项（推测）。这三个约束的对象数分别为 14,312、85、2,395。

5. **字段名容易误读（已验证）**。`template_selector_u16_at_12` 中的 `12` 是十六进制字节偏移 0x12（十进制 18），不是 u16 下标 12。描述模板用的是 u16 下标 12（字节 0x18）。两者不要混淆。

6. **main_kind 与 genera 是原程序内部编号（静态证据）**。它们不是 Java 或界面上的编号，目录没有给出映射。genera 对应的语义（例如 14 可能是线段）只是推测。

7. **2000 头部也有类型字段，编号可能不同（静态证据，未入脚本）**。kind 2000 的载荷有 28 字节和 16 字节两种布局（语料中分别为 360,923 和 39,821 个，已验证）。一次性探查发现：载荷内偏移 0x06 处的 u16（下标 3）与约束表的 main_kind 在约 69%（277,108 / 400,744）的对象上相同；偏移 0x08 处的 u16（下标 4）与 genera 在约 23%（93,255 / 400,744）上相同。两者都没有完全一致，说明头部编号与约束表可能不同（推测）。本目录只用约束表的值。这段探查代码未放进脚本，需要时可以重做。

8. **描述模板随仓库提交**。`description_template` 的文字来自 `reference/features/resource-text.json`，整份资源导出属于本机保存的第三方内容、不入库；目录里只引用约 110 条短描述句，用于识别对象类型，随 `spec/` 提交。

9. **example_files 是挑选的结果（已验证）**。它只是体积最小的几个文件，不代表该对象最典型的用法。
